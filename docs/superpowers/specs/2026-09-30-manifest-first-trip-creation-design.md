# Manifest-first trip creation — design

**Date:** 2026-09-30 (revised the same day after review)
**Ticket:** FP-281 (replaces the draft → confirm approach in its description)
**Status:** Awaiting written-spec review.
**Supersedes for FP-281:** option B of [`2026-09-26-trip-creation-workflow-proposal.md`](../../design-notes/2026-09-26-trip-creation-workflow-proposal.md).

## 1. Decision

The dispatcher types a **manifest number**. FreightProof pulls that manifest from Parcel Perfect (mocked — there is no live integration) and fills in everything the manifest can supply: the client, the route, the planned times, and every waybill and parcel. The dispatcher enters only what the manifest cannot supply — driver, horse and trailers, plus times or precincts in the rare case the manifest lacks them — and creates the trip.

The manifest is pulled **once, at creation**. A snapshot of it is stored and covered by the journey lock. There are no drafts.

The manifest replaces the order number as the trip's external key. **The order number is removed** from the system: from the API and UI first, then from the database in a follow-up clean-up (§17).

## 2. Why

**Drafts are planning, and planning is out of scope.** FreightProof needs a Trip only before the driver's first evidence event. Bruce, 28 Jul §8–9: contract routes are fixed weeks ahead and ad-hoc bookings are same-day, and in both cases the client creates the manifest around 12:00 on the day and LFG confirms the vehicle then. Every booking reaches FreightProof on the day.

**The manifest is what a linehaul departure is.**

| Fact | Source |
|---|---|
| "Container" = manifest = the whole load for one departure | Bruce 28 Jul §5 |
| The client creates it in PP; only the departing branch does | Bruce 5 May §4.1, 28 Jul §2.1 |
| LFG's Master Waybill references the client's manifest number and totals the load | Bruce 5 May §4.1 |
| It is uploaded to PP at sealing | Bruce 16 Apr §2.2 |
| PP generates manifests "for each of your line-haulers to your destination hubs" and imports manifests from other PP companies "electronically … with 100% accuracy" | Parcel Perfect product description |

A FreightProof trip is, in effect, LFG's Master Waybill made digital: one departure, pointing at one client manifest.

## 3. Goals and non-goals

**Goals**

- A loaded trip is created from a manifest number plus driver, horse and trailers.
- One non-cancelled trip per manifest, enforced by the database under concurrency; a retry after a timeout finds the existing trip.
- The journey lock covers the manifest key, the manifest snapshot and the planned times.
- The order number is gone from the API and UI, and later from the schema (§17).

**Non-goals** — see §14 (later) and §13 (known limitations).

## 4. Terminology

"Manifest" already means something in this codebase: the trip's cargo listing (`manifest_service`, `GET /trips/{id}/manifest`, `ManifestPanel`, `types/manifest.ts`). To avoid two meanings:

| Term | Meaning | In code |
|---|---|---|
| **PP manifest** | The client's Parcel Perfect manifest this spec is about | `pp_manifest_*` names throughout |
| **Waybill** | One PP waybill on the manifest | Stored as a `Consignment` row — see below |
| **Parcel** | One barcoded item on a waybill | `Parcel` (unchanged) |

The hierarchy is **PP manifest → waybill → parcel**.

**Consignment vs waybill.** A `Consignment` row *is* one waybill on a trip: the table is unique on `parcel_perfect_reference` ("one waybill, one consignment row", FP-138). In logistics usage the consignment is the goods and the waybill is the document describing them, so the name is correct. Renaming the table would touch about 94 files across every developer's area for no behavioural gain, so it is out of scope. The UI calls them waybills, as it already does.

## 5. Where each part of a trip comes from

| Source | Fields |
|---|---|
| **The PP manifest** | Client (`client_organization_id`), the manifest key (§6), origin and destination precincts (from hub codes, §7.2), `planned_departure_at`, `planned_arrival_at`, `trip_type = loaded`, the two `TripStop` rows, every waybill (`Consignment`) and its parcels (`Parcel`), the client's order reference if the manifest carries one (kept in the snapshot, displayed read-only) |
| **Dispatcher — always** | Manifest number, driver, horse, trailers (zero or more) |
| **Dispatcher — only when the manifest can't supply it** | Planned departure or arrival when the manifest has none (both are editable if the manifest has them); origin or destination precinct when a hub code isn't linked to a precinct |
| **Generated by FreightProof** | `id`, `trip_reference`, `operator_organization_id`, `created_by_user_id`, `created_at`, `status`, `current_phase`, `current_stop`, the phase plan, the manifest snapshot, `journey_lock_hash`. Each trailer's Pulsit device ID is copied from the vehicle record |
| **Filled in later by the trip itself** | `actual_departure_at`, `actual_arrival_at`, `closed_at`, `idvs_check_status`, `idvs_checked_at`, `pulsit_trip_reference_id` |
| **No longer captured** | Order number (removed), `template_id` (always null), pallet/unit counts (deferred) |

**Why driver, horse and trailers are not taken from the manifest:** they are LFG's decision. The client records them on the manifest only as a copy of what LFG tells them (Bruce 16 Apr §2.1), and usually not yet at 12:00. Taking them from the manifest would pre-fill LFG's choice from the client's copy of it, and would mean storing driver ID numbers in a record that cannot be erased (POPIA).

**Empty legs** (no manifest): the dispatcher enters origin, destination, times, driver, horse and trailers, as today.

## 6. Identity: the manifest key

The dispatcher types only the number. The trip stores:

```
(operator organisation, issuer PP account number, origin hub code, manifest number)
```

The issuer account and origin hub come from the manifest header. In real PP, numbers are unique only within one client's system and may restart per branch; storing the issuer and hub keeps duplicate detection correct whichever is true. **The mock treats manifest numbers as globally unique**, which is what lets the dispatcher type the number alone. A waybill's PP account number (`accnum`) identifies the client — e.g. RTT — not the client's own customer.

**Every waybill on a manifest must carry the issuer's account.** The trip takes its client from the manifest header, while each consignment takes its client from its own waybill's `accnum`. A mixed manifest would give one trip two conflicting clients, so it is refused (`WAYBILL_CLIENT_MISMATCH`, §10.1).

**Rules**

- **One non-cancelled trip per manifest.** A closed trip still blocks reuse: a manifest is one departure.
- **Cancelling a trip frees its manifest**, subject to §10.5.
- **Empty legs have no manifest key.** The database ignores nulls in the unique index.
- **`trip_reference`** (`FP-YYYYMMDD-XXXXXXXX`) remains FreightProof's own identifier, used by the driver app, Hedera anchoring and exception records.

**The order number is removed.** Nothing in PP reliably supplies it, typing it adds no evidence value, and an auto-generated one would duplicate `trip_reference`. Its jobs move:

| Old job | New owner |
|---|---|
| One live trip per order | Manifest key unique index |
| Wizard retry-after-timeout lookup | Exact manifest-key filter on the trip list |
| Label and search in dispatcher views | Manifest display (e.g. `CGY Logistics · JNB 69`), or "Empty leg" |
| Label in the driver app | `trip_reference` |
| Journey-lock payload key | Removed (§9) |

## 7. Data model changes

One hand-written Alembic migration (autogenerate is not safe on this repo — see CLAUDE.md), named `<YYYY_MM_DD>_ciaran_pp_manifest_trips.py` with the date it is written. Ciaran applies it from `dev` after merge. A second, later migration drops the order-number column (§17).

### 7.1 `trips`

| Change | Detail |
|---|---|
| `order_number` → nullable | Nothing writes it any more. Drop `uq_trips_live_order_number`. The column and `ix_trips_order_number` are dropped by the clean-up migration (§17) |
| Add `pp_manifest_issuer_account` | `String(6)`, nullable — matches `Organization.pp_account_number` |
| Add `pp_manifest_origin_hub` | `String(10)`, nullable — PP hub code, e.g. `JNB` |
| Add `pp_manifest_number` | `Integer`, nullable |
| Check constraint | The three columns are all null or all set |
| Unique partial index `uq_trips_pp_manifest` | `(operator_organization_id, pp_manifest_issuer_account, pp_manifest_origin_hub, pp_manifest_number) WHERE status <> 'cancelled'`, also declared in `Trip.__table_args__` so autogenerate drift doesn't grow |

The key lives on `trips`, not in its own table, because the uniqueness rule depends on the trip's status and a Postgres partial index cannot look across tables.

### 7.2 `precincts`

Add `pp_hub_code` (`String(10)`, nullable), unique per `(principal_organization_id, pp_hub_code)` where set, declared in `__table_args__`. A manifest's hub resolves to the precinct owned by the issuing client with that hub code. Seed scripts set the demo hub codes; editing them in the precincts UI is out of scope.

### 7.3 No other schema changes

- The manifest snapshot is stored in the **existing, never-written** `PhaseEvent.parcel_manifest_snapshot` JSONB column ([phases.py:144](../../../backend/app/db/models/phases.py)) on the trip's `trip_creation` phase row (H0). No new table, enum or model registration.
- **The snapshot is dispatcher-only.** The field is removed from [`PhaseEventRead`](../../../backend/app/schemas/phases.py), where it is exposed today (always null). Otherwise every trip response would carry the whole manifest: the driver would receive it through `GET /trips/me/active` and `GET /trips/me/{trip_id}`, and it would be resent on every dispatcher poll of the trip. Dispatchers read it through the dispatcher branch of the existing role-aware `GET /trips/{id}/manifest`; the driver's linehaul branch never includes it.
- `consignments` is unchanged. `unit_count_expected` stays null for manifest trips (pallets deferred); the driver's unit count falls back to the parcel count, as it already does when units are empty ([manifest_service.py:131](../../../backend/app/orchestration/manifest_service.py)).

## 8. Mocked Parcel Perfect manifest

In [`integrations/parcel_perfect.py`](../../../backend/app/integrations/parcel_perfect.py). This is an **assumed data contract**: PP holds manifests, but its ecomService API exposes only `getSingleWaybill`. The code labels it as such. The UI does not (decided 2026-10-01): it presents the manifest as coming from the client's parcel system, in neutral terms, so the screen stays the same whichever system supplies it.

```python
@dataclass
class PPManifestNote:
    noted_at: datetime   # UTC
    operator: str
    text: str

@dataclass
class PPManifestHeader:
    manifest_number: int
    issuer_account: str             # PP accnum of the client (e.g. RTT)
    issuer_name: str
    origin_hub: str                 # e.g. "JNB"
    destination_hub: str            # e.g. "DUR"
    created_at: datetime            # UTC
    closed_at: Optional[datetime]   # None until the client closes the manifest
    planned_departure_at: Optional[datetime]
    expected_arrival_at: Optional[datetime]
    client_reference: Optional[str]
    notes: list[PPManifestNote]

@dataclass
class PPManifestResponse:
    header: PPManifestHeader
    waybills: list[PPWaybillResponse]   # identical shape to getSingleWaybill
```

- **`get_manifest(manifest_number) -> PPManifestResponse`** on the mock client; raises `PPManifestNotFoundError`. The real client raises `PPUnsupportedError`.
- **Waybills come from the existing source.** The mock selects waybills whose own `manifest` field equals the number — exactly what `get_waybills_by_manifest` does today, including staged overrides — and adds a header fixture per manifest. There is one source of truth for which waybill is on which manifest. `get_waybills_by_manifest` and `GET /pp/manifests/{n}` are removed once nothing calls them. Fixtures 69 and 70 are asserted by existing tests and are not modified; new manifests get new numbers.
- **Times.** PP's date strings carry no timezone. The parser reads them as South African time (`Africa/Johannesburg`) and converts to UTC; everything downstream is UTC.
- **Totals** (waybills, parcels, weight) are computed from the waybills, never stored in the header.
- **Demo staging.** A dev-only trigger can set a header's times and closed state, and the existing waybill override can move a waybill between manifests.
- **Mock fixtures** include: a closed manifest with times; an open manifest with no times (the 12:00 case); a manifest whose destination hub is linked to no precinct; a mixed-client manifest. Manifest 70's existing waybills already carry two accounts (`UNMAP9` and `MOCK01`), so it gets a header and serves as the mixed-client case without modifying its waybills.

## 9. Journey lock

[`compute_trip_canonical_payload`](../../../backend/app/crypto/hashing.py) is replaced by a **fixed key set** — every key always present, null when absent — so reconstruction has one deterministic shape:

| Key | Value |
|---|---|
| `trip_id`, `driver_id`, `horse_id`, `trailers`, `origin_precinct_id`, `destination_precinct_id`, `created_by_user_id`, `created_at`, `trip_type` | As today |
| `pp_manifest` | `{issuer_account, origin_hub, number}`, or null for empty legs |
| `pp_manifest_snapshot_sha256` | SHA-256 of the canonical snapshot, or null |
| `planned_departure_at`, `planned_arrival_at` | Or null |
| `order_number` | **Removed** |

- **Canonical form.** All datetimes are converted to UTC before serialising (a request carrying `+02:00` must hash the same as the UTC value Postgres returns). Serialisation uses the module's existing convention: `json.dumps(sort_keys=True, separators=(",", ":"))`. The snapshot hash uses the same canonical form.
- **Verification recomputes the snapshot hash** from H0's stored `parcel_manifest_snapshot` rather than trusting a stored hash, so editing the snapshot shows as tampering.
- **No payload version.** No trip on the dev database has an anchored journey lock: seeded trips are written with `journey_lock_hash = NULL` and never anchored ([`seed_trips.py`](../../../backend/scripts/seed_trips.py)). The old shape and the `trip_type` presence check in [`verification_service`](../../../backend/app/orchestration/verification_service.py) are removed. Any trip anchored through `POST /trips` on a local database before this change will verify as tampered and should be re-created.
- Only hashes and identifiers reach Hedera. The snapshot itself, which includes waybill contact details, stays in Postgres.

Phase-receipt payloads (loading v2 and the rest) are not touched.

## 10. Backend

New orchestration module `orchestration/pp_manifest_service.py` holds the manifest logic; the endpoints stay thin. Pure helpers (canonical snapshot, totals, hub resolution) have no I/O and are unit-tested directly.

### 10.1 Preview — `GET /api/v1/trips/pp-manifest-preview?manifest_number=69` (tag `trips`)

Read-only; writes nothing. Declared before `GET /trips/{trip_id}` in the router, or FastAPI matches the static path as a trip id and rejects it. Response `PPManifestPreviewResponse`:

- manifest key, display string, `snapshot_sha256`
- client name and organisation (or a warning if the account is linked to no organisation)
- origin and destination hubs, each with its resolved precinct or null
- planned departure and arrival, or null; closed or not; client reference; notes
- totals, and a line per waybill: number, destination town, parcels, weight
- warnings, each with a code:

| Code | Blocks creation? |
|---|---|
| `MANIFEST_ALREADY_ON_TRIP` (with that trip's id and reference) | Yes |
| `CLIENT_NOT_LINKED` (issuer account matches no organisation) | Yes |
| `WAYBILL_CLIENT_MISMATCH` (a waybill's account differs from the issuer's) | Yes |
| `WAYBILL_ON_OTHER_TRIP` | Yes |
| `NO_WAYBILLS` | Yes |
| `ORIGIN_HUB_UNLINKED`, `DESTINATION_HUB_UNLINKED` | No — the dispatcher picks the precinct |
| `NO_PLANNED_TIMES` | No — the dispatcher enters them |
| `MANIFEST_NOT_CLOSED` | No — informational (see §13) |

### 10.2 Create — `POST /api/v1/trips/from-pp-manifest` (tag `trips`)

Request `TripFromPPManifestRequest`: `manifest_number`, `expected_snapshot_sha256`, `driver_id`, `horse_id`, `trailer_ids`, and optional `planned_departure_at`, `planned_arrival_at`, `origin_precinct_id`, `destination_precinct_id`. Cargo is never accepted from the client — the server pulls it.

Server steps, in one transaction, fail-closed as today:

1. Fetch the manifest. If its snapshot hash ≠ `expected_snapshot_sha256` → 409 `MANIFEST_CHANGED` with a fresh preview; nothing is saved.
2. Resolve the client organisation and both precincts (manifest first, request values only where a hub is unlinked).
3. Merge times (request overrides manifest). A planned departure is required after merging — a trip without one can never be activated. Run `validate_declared_schedule` on the merged values.
4. Validate driver, horse and trailers (existing checks).
5. Check for a non-cancelled trip with the same key (friendly 409), then insert. A lost race surfaces on flush as the unique-index violation and returns the same 409 `MANIFEST_ALREADY_ON_TRIP` — the check-then-constraint pattern the order number uses today.
6. Create one consignment per waybill **from the waybill data already in the manifest** — no second PP call. `fetch_and_sync_consignment` is split so a caller holding a `PPWaybillResponse` can sync it directly.
7. Create the two stops and the phase plan (existing single-leg path).
8. Store the canonical snapshot on H0's `parcel_manifest_snapshot`.
9. Compute the journey lock (§9), anchor it (existing), complete H0.

### 10.3 `POST /api/v1/trips` (existing)

Kept for empty legs (the new screen's "No manifest" option), multi-stop trips, seeds and tests. The only change is that `order_number` is removed from the request. This path has no duplicate key after that removal; a retried empty leg can be cancelled.

### 10.4 Retry after timeout

The screen looks for a non-cancelled trip with the same manifest via an **exact** filter on the trip list (`pp_manifest_number=69`). The existing `q` search is a substring match — "69" also matches "690" — so it is not used for this.

### 10.5 Cancel and recreate

`fetch_and_sync_consignment` currently refuses to move a waybill off any other trip. It will allow a move **from a cancelled trip, only when none of that waybill's parcels has a scan timestamp**. Otherwise it returns 409 explaining that the parcels were scanned on the cancelled trip.

The reason: there is one set of `Parcel` rows per waybill, and scan timestamps keep the first scan ([scan_service.py:287](../../../backend/app/orchestration/scan_service.py)). Moving scanned parcels would carry the old trip's scans onto the new one, and the real reload scans would be ignored. Handing a loaded manifest to another truck after a breakdown is a separate feature (§14). The cancelled trip keeps its H0 snapshot, so its cargo stays explainable.

### 10.6 After creation

The existing 60-second PP poll keeps refreshing each waybill and may add parcels. The H0 snapshot is the record of the manifest **at creation**; later PP updates are expected and do not alter it.

### 10.7 Errors

| Case | Response |
|---|---|
| Manifest not found | 404 |
| Manifest lookup unsupported (live PP) | 501, "Manifest lookup is not available on the live Parcel Perfect API" |
| PP unreachable or errors | Same mapping as the existing PP endpoints |
| Manifest already on a non-cancelled trip | 409 `MANIFEST_ALREADY_ON_TRIP` with that trip's id and reference |
| Manifest changed since preview | 409 `MANIFEST_CHANGED` with a fresh preview |
| A waybill is on another live trip, or scanned on a cancelled one | 409 |
| Client not linked, a waybill's client differs from the manifest's, no waybills, unlinked hub with no precinct given, no planned departure after merging, schedule invalid | 422 |
| Hedera anchoring fails | Whole trip rolls back (existing) |

`TripConflictError`, `_check_order_number_conflict` and `OrderNumberStr` are replaced by a manifest equivalent (`PPManifestAlreadyOnTripError`).

## 13. Known limitations of this version

- **Live PP cannot create loaded trips.** The real API has no manifest lookup; the screen shows the 501 message. Loaded trips are demonstrable only against the mock.
- **Changes to the manifest after creation are not picked up.** A waybill added later is not on the trip; a waybill removed later shows as missing at loading. The preview warns when a manifest is not yet closed.
- **The driver's unit count is the parcel count**, until pallets are added.
- **`POST /trips` has no duplicate key** once the order number is removed.
- **A manifest whose parcels were scanned cannot be moved to a new trip.**

## 14. Later

- **Second pull at loading** (committed snapshot): must run before scan ingest, needs a loading payload v3, a "client record disagrees" exception type rather than "substitution", and a decision on timing relative to sealing.
- **Breakdown after loading** — handing a loaded manifest to another truck. Likely modelled as a vehicle change on the same trip through an exception event, not cancel and recreate.
- Pallet counts from the manifest.
- Vehicle and driver from the manifest, and a cross-check against the trip.
- More than one manifest per trip; multi-stop trips in the new screen.
- Trip templates.
- Live PP manifest lookup — querying the origin client's PP.
- Optionally renaming `consignments` to `waybills`.

## 15. Acceptance scenarios

These replace the seven in the 26 Sep proposal.

1. **From a manifest number.** The dispatcher types the number, sees the client, route, times, waybills and parcels, picks driver, horse and trailers, and creates the trip. The lock covers the manifest key, snapshot hash and planned times.
2. **No duplicates.** Two concurrent creates for one manifest produce one trip; the other gets 409 naming it. A timed-out retry finds the existing trip.
3. **Cancel and recreate before scanning.** Recreation succeeds, the waybills move, and the cancelled trip's snapshot and lock still verify.
4. **Cancel after scanning.** Recreation is refused with an explanation.
5. **Changed before creating.** A manifest that changes between preview and create returns 409 with the new summary; nothing is saved.
6. **Gaps in the manifest.** A manifest with no times, or an unlinked hub, prompts the dispatcher for exactly those values and the trip is created.
7. **Live PP.** Manifest lookup returns 501 with a clear message.
8. **Empty leg.** Created without a manifest or order number.
9. **Driver view.** The driver sees the trip reference and unit count, no manifest contents.
10. **Tamper-evident.** A new trip verifies; editing the stored snapshot or a locked trip field makes verification fail.
