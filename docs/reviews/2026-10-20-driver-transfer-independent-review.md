## Findings, ordered by severity

All source defects listed here were reproduced before repair. References identify the final repair sites, not obsolete pre-repair line numbers.

1. **P1 — A GPS wait could continue under another account generation, including A→B→A. Fixed.** `frontend/driver-pwa/lib/context/LocationContext.tsx:83` and `frontend/driver-pwa/lib/submission/phase-submitter.ts:269`. Navigation recorded its fix after the account changed; phase sending captured its network generation only after GPS had resolved. This allowed later requests from the wrong pipeline. The backend still enforces access; the reproduction proves wrong-account attempts, not a successful authorization bypass. The phase fallback cache also reused A's location for B when B had no fix, which could falsely attribute A's location to B on B's own otherwise-authorized trip. GPS continuations now stop and retain the original actor/period; the cache is generation-scoped. Both A→B and A→B→A cases and cross-account fallback have permanent tests.

2. **P1 — Delayed auth session lookups could revive a signed-out actor. Fixed.** `frontend/driver-pwa/lib/context/AuthContext.tsx:87` and `:137`. Startup and interactive sign-in lookups could finish after manual sign-out and bind the old profile in the new generation. Reproductions returned the old user and a non-null actor after sign-out. Both lookup continuations now check their starting generation; null sessions do not bind a driver. Real-mode sign-in fixtures now model an actual authenticated session, rather than a successful profile load with no session.

3. **P1 — Not every upload/save/receipt boundary retained its original actor generation. Fixed.** `frontend/driver-pwa/lib/api/driver-substitutions.ts:72` and `:104`, `lib/api/artifacts.ts:100`, `lib/hooks/useOfflineQueue.ts:610`, `lib/hooks/useSubstitutionCapture.ts:462`. Multipart callers could resume after conversion and acquire the current transport generation; a report waiting on its save lock could restart after A→B→A; a safely completed confirmation could initiate a new context request after the account switched. Guards now cover the outer awaits, not only inner helpers. Stored photos, keys and safe receipts remain with their original actor. Regressions assert no later POST/context fetch and retained original data.

4. **P2 — Invalid browser sample timestamps escaped the callback and left capture unresolved. Fixed.** `frontend/driver-pwa/lib/hooks/useLocation.ts:92`. The native path caught conversion failures, but the asynchronous browser callback threw outside the Promise executor. The new regression invokes a later callback with an invalid timestamp. It now rejects into the existing unavailable/unknown result instead of throwing globally or hanging B's acceptance. No fake timestamp or location is introduced.

5. **P2 — Correction reconstruction ignored an unknown frozen payload version. Fixed.** `backend/app/orchestration/verification/substitution_payloads.py:176`, `substitutions/anchors.py:298`, `verification/service.py:257`. A correction marked version 99 was reconstructed as v1: integrity was merely pending and recovery could anchor it. Reconstruction now validates the frozen version/kind, chain reads report failed integrity, and recovery refuses it. V1 canonical builders were not changed by this repair. The regression also checks that the old hash remains unchanged and no hash is submitted.

6. **P2 — Completed detail showed notification policy but omitted recorded notification facts. Fixed.** `backend/app/orchestration/substitutions/reads.py:384`, `backend/app/schemas/driver_substitutions.py:441`, `frontend/dispatcher/components/trips/DriverTransferDetail.tsx:27`. The plan required actual notice facts; a generic statement that A is notification-only did not supply them. Added the outgoing driver's existing request-scoped durable notices, creation/read timestamps and an explicit historical-unknown state. Creation/read are not labelled delivery or consent. This is an additive dispatcher projection, documented in the v2 contract, with no new table or migration.

7. **P2 — Acceptance and surviving-path verification remain incomplete. Open release blocker.** See the Task 11 requirements in `docs/superpowers/plans/2026-10-20-driver-transfer-safety-and-simplification-implementation.md` and the matrix below. The 79 driver failures cannot be called green; real phone/native/storage/worker/tracker/Hedera acceptance has not happened. The final backend static failures include pre-existing debt and an existing size baseline to which this implementation adds two trip-schema lines. These are reported rather than waived. They do not establish a failure of the new migration, and they do prevent claiming the complete approved plan or candidate release is accepted.

## Architecture and implementation quality

The core approach is appropriate for this repository: retain the original journey lock/driver, append completed custody rows, dispatch by persisted request/payload version, derive required roles once, reuse notices and transaction hooks, and interleave read-only transfer rows around the existing phase cards. The immediate form and single page-level controller avoid a second initiation workflow. The v1 replay adapter is justified: it preserves historical/internal lifecycle behavior while rejecting unaccepted old public creates. Removing it merely to reduce a file would weaken the upgrade boundary.

The review repairs keep these choices and add no dependency, event framework, duplicate custody table or alternative location service. The migration remains narrowly additive and unchanged by this review. A dispatcher recheck does not create B's acceptance, and A's absence does not become an attestation.

Optional improvements, separate from release blockers:

- `reads.py:384` builds every completed summary to select one detail, then verifies the whole chain; `_confirmation_details` also looks up completion again. Reuse a single-row summary adapter and batch the shared facts if transfer history grows. Preserve authorization and local receipt binding while doing so.
- `request_read.py:110` performs repeated refresh/driver/vehicle/capture/eligibility queries for each request history item. Batch immutable completed/cancelled history and calculate live eligibility only for the pending request. This is a concrete query-volume opportunity, not a requirement for a new read architecture.
- Auth restoration and interactive sign-in still contain separate profile-loading paths. A future focused consolidation could reduce duplicate loads and the number of stale-result guards. Do not undertake that refactor during acceptance unless another regression requires it.
- Transfer detail attributes actors and seal vehicles by stable IDs; adding authorized display labels and photo-to-vehicle captions would make review easier. IDs remain the evidence references and current names must remain labelled as display names.
