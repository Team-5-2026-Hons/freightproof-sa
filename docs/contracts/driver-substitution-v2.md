# Driver substitution API contract v2

Owner: Ciaran. Implementation authorised 20 October 2026. Ciaran owns all changes and migrations and will review and run migrations after implementation. No deployment or shared database upgrade is authorised. Historical v1 contract and canonical bytes remain unchanged.


These are concrete design choices for review, not placeholders an executor may reinterpret silently.

**User-confirmed workflow amendment (20 October):** new v2 is dispatcher authorisation → B acceptance → server-effective completion; A is notified only. A keeps live access until completion, B gets no early live-write authority, and A's connection/read acknowledgement is irrelevant to completion. Persistent in-app arranged/completed notices use the existing notice system; no new push/SMS/email delivery is implied. Opening A's notice never captures a new location. Keep B's existing vehicle/seal/photo checks; removing those checks was not requested. This replaces the earlier two-independent-confirmations requirement for new requests only.

**Required roles:** add pure `required_confirmation_roles(request_format: str) -> tuple[SubstitutionRole, ...]` to `orchestration/substitutions/request_read.py`, returning `(OUTGOING, INCOMING)` for planned_v1 and `(INCOMING,)` for immediate_v2. Use it for missing_confirmations, permitted_actions, completion_blocked_by readiness and service completion; reject unknown formats. V2 outgoing context is notification/read-only for substitution capture routes; no confirm_outgoing action, outgoing upload or declaration. B's single valid acceptance completes normally when eligibility passes; PENDING identity retains it for the existing admin attestation/recheck. V2 dispatcher complete cannot bypass absent B acceptance, and A's absent declaration needs no missing_confirmation_reason. Legacy v1 both-role/explicit missing-confirmation override rules remain unchanged. To adopt v2, replace a legacy pending request explicitly with a fresh request and no inherited captures.

Expose `request_format`, `confirmation_policy: 'two_driver_v1' | 'incoming_acceptance_v2'` and `required_confirmation_roles: SubstitutionRole[]` on request reads/shared types so clients do not infer required actors from confirmation count. Archived v1 operation responses may omit these new read fields and receive v1-compatible read defaults without rewriting stored result_json or request digests. Extend `permitted_actions` with a keyword-only `required_roles` argument defaulting to the v1 tuple for old pure callers; all production request reads pass the format-derived tuple explicitly. Keep request-less legacy completed summaries' policy fields null when never recorded.

**Seal evidence:** v2 validates B's own checks/photos and records genuine damaged/missing-seal findings from that acceptance, scoped/idempotent as today. It must not run compare_seal_captures with an invented outgoing reading or claim an A-versus-B mismatch. Add a small single-capture compromised-seal path; preserve v1 pairwise comparison. Cross-phase historical seal comparison is outside this change; existing ordinary phase findings still work.

**Three versions:** `request_format: 'planned_v1' | 'immediate_v2'` describes persisted request semantics. Existing `version`/`expected_version` remain optimistic concurrency counters. `payload_version` remains the immutable anchored format (1 or 2); corrections stay v1. V1 operation parsers/digest serialization remain unchanged and contain no newly defaulted fields.

**New immediate body:** `ArrangeImmediateSubstitutionRequest` has `client_request_id`, `request_format: Literal['immediate_v2']`, `incoming_driver_id`, `reason` using the existing 1–1000 trimmed nonblank validator. `ReplaceImmediateSubstitutionRequest` adds `expected_version` and `replacement_reason`. New requests supply no exchange, expected time or planned flag. Keep unchanged legacy `ArrangeSubstitutionRequest`/`ReplaceSubstitutionRequest` models for parsing/replay, with a union at the existing endpoints. Authenticate/tenant-scope, calculate the matching format's digest, return an exact accepted replay, enforce flag-off, then reject an unaccepted legacy create/replace with 422 `Refresh the dispatcher before arranging a new transfer.` No new public error code is necessary.

**Storage:** new requests explicitly persist `request_format='immediate_v2'`, `reservation_start_at` from the server's accepted-action clock, and null legacy `exchange_label/latitude/longitude/instructions`, `expected_at`, `is_planned`. Existing rows receive only format metadata `planned_v1`; preserve every old planning, confirmation, operation and hash value. Completed `exchange_location` and `is_planned` become nullable for new no-plan rows; no invented text or `false` classification. Database checks enforce the two request shapes. Immediate reservation is `[reservation_start_at, infinity)` until completion/cancellation/terminal trip; completion uses the existing remaining-trip occupancy rule. Legacy scheduled windows remain unchanged.

**Observation:** keep `captured_at` as declaration time and the existing `ConfirmSubstitutionRequest` parser unchanged. Add `ConfirmSubstitutionObservationRequest` extending it with required `capture_format: Literal['observation_v2']`, `location_observed_at: aware datetime | null` and `location_unavailable_reason: 'permission_denied' | 'timeout' | 'position_unavailable' | 'unknown' | null`. The two nullable fields are explicit on a new body; legacy bodies have no discriminator/new fields and use their unchanged parser/digest. Use that union on the existing confirmation endpoint/service and in the stored client submitted-body type. All three coordinate/accuracy fields remain together. Old stored metadata missing the new fields reads as null; do not enrich an already-frozen outgoing body. Device sample timestamp, not callback/declaration time, populates observation time. Reject inconsistent supplied location/reason combinations. V1 pending requests accept their original confirmation bodies unchanged. A new phone may attach supplemental observation metadata to a v1 request, but it is not retrospectively covered by the v1 custody hash; detail/audit must state that coverage truthfully.

**Payload:** preserve v1 builder output byte-for-byte. V2 omits `is_planned`, `exchange_sha256`, `expected_at`; adds `request_format`, `reservation_start_at`, `confirmation_policy: incoming_acceptance_v2`, `required_confirmation_roles: [incoming]`; retains original custody/actor/licence/identity/capture commitments and adds each capture's observation time and enumerated unavailable reason. V2 keeps the outgoing capture explicitly null/not requested and includes the actual incoming capture; absence of A is not a missing required confirmation. Commit the policy and actual authorising/accepting actors. Only the resulting hash goes to Hedera. V1 completion after upgrade still freezes v1 with its actual role/attestation facts. Rebuild from receipt version when verifying a receipt, from frozen row version when recovering, and from persisted request format on first completion. Reject unknown versions or inconsistent row/payload versions; never silently default to latest.

**Completed read:** retain existing request-list fields. Add dispatcher-only `TripDetailResponse.completed_driver_substitutions: CompletedSubstitutionSummary[]` (shared `Trip` field optional for old-server compatibility). Summary also carries `request_format` (nullable for request-less legacy), `required_confirmation_roles` (nullable for unknown legacy policy) and `confirmation_policy` (nullable for unknown legacy policy). Other summary fields: `substitution_id`, `request_id: UUID|null`, `sequence_number`, `outgoing: DriverContact`, `incoming: DriverContact`, `effective_at`, nullable `completion_mode`, nullable `anchor_status`, nullable `receipt_id`, and `phase_context: {phase_event_id, phase_type}|null`. Detail extends it with nullable `reason`, full `confirmations`, scoped `artifacts`, `corrections`, nullable `arranged_by_user_id`, nullable `completion`, nullable `identity_attestation` (author/reason/server time), nullable `declared_exchange_at` and `missing_confirmation_reason`, and `custody_integrity`. For new v2 show A: Not requested — notification only, not Missing confirmation. Confirmation detail carries independent coordinates/accuracy/observation/reason/assessment plus `location_observation_committed: bool`, derived from payload coverage. Use existing schema types for declarations/artifacts/corrections; do not invent parallel seal DTOs.

**Routes:** add `GET /api/v1/trips/{trip_id}/driver-substitutions/completed/{substitution_id}` on the existing dispatcher router, returning `CompletedSubstitutionDetail`. Same-org dispatcher only; 401 unauthenticated, existing role denial for drivers, 404 unrelated/cross-org/missing record. No new router/main.py registration. Load completed rows directly, then optional request detail. Driver context/history remain separately scoped.

**Timeline:** insert read-only transfer rows as siblings around the existing TimelinePhase cards. Use valid server phase completed_at boundaries and transfer effective_at; never globally re-sort phases or use device/planned times. Example: Loading completed 10:00, transfer effective 10:05, Departure completed 10:10 ⇒ Loading → Driver transferred → Departure. During an unfinished phase, the event follows the last completed milestone and precedes that phase's completion card; show During in transit/loading only when historical context is proven. Existing nested events remain inside their cards: this is chronological milestone placement, not a rewrite to merge every nested event into one rail.

Add pure `positionDriverTransfers(phases: readonly PhaseDescriptor[], events: readonly CompletedSubstitutionSummary[]): DriverTransferPlacement` in dispatcher `lib/phase/driver-transfers.ts`. Define `DriverTransferPlacement {beforeFirst: readonly CompletedSubstitutionSummary[]; afterPhase: ReadonlyMap<string, readonly CompletedSubstitutionSummary[]>; unplaced: readonly CompletedSubstitutionSummary[]}`. Input phases are plan-ordered. Deduplicate by substitution ID; place against the latest consistent completed boundary at/before effective_at and before the next later completion. Unknown future phases keep plan order. Sort events sharing a slot by effective_at, then sequence_number, then stable ID; equal phase/event timestamps render the phase first and label Same recorded time without inventing causal order. Inconsistent/missing historical timestamps go to a dated Unplaced historical driver transfers section only; do not use it to avoid placing new events. Preserve stable keyed phase wrappers so refresh/inserting a transfer cannot remount existing expanded cards. No new PhaseAct kind, exception record or progress calculation.


## Wire examples

IDs below are fictional examples.

```json
{"client_request_id":"10000000-0000-4000-8000-000000000001","request_format":"immediate_v2","incoming_driver_id":"10000000-0000-4000-8000-000000000002","reason":"Driver replacement"}
```

Adding exchange/expected_at/is_planned to that body, omitting the format discriminator, or an unknown format is invalid for a new immediate create. An exact already-accepted v1 arrange/replace still replays its original stored result; an unaccepted legacy create/replace returns 422: Refresh the dispatcher before arranging a new transfer. Existing v1 confirm bodies remain unchanged and replay their original digest.

A new missing-GPS declaration explicitly carries `capture_format: observation_v2`, `latitude: null`, `longitude: null`, `accuracy_metres: null`, `location_observed_at: null`, `location_unavailable_reason: permission_denied` (or another supplied enumerated reason). This does not block eligible completion. Legacy null GPS remains unknown. New v2 required roles are `[incoming]`, outgoing capture is null/not requested, and dispatcher completion without B acceptance returns 422. V1 required roles remain `[outgoing, incoming]` with its original explicit attestation rules.

Request-less legacy completed detail carries `request_id: null`, `request_format: null`, `confirmation_policy: null`, `required_confirmation_roles: null`, `reason: null`, `confirmations: []`, `completion: null`, `identity_attestation: null`, `phase_context: null` when unrecorded. It must not claim verified declarations.

## Delivery gates

Independent review addition: completed dispatcher detail includes `outgoing_notices: SubstitutionNoticeRead[]`, scoped to the recorded outgoing driver and request. These are durable notice creation/read facts, never delivery receipts or consent. Request-less legacy detail returns an empty list; the UI states that notification facts were not recorded. Existing driver access rules and the notice system are unchanged.
