## Part 0 — The one-sentence version

> **We stopped storing where a trip is, and started deriving it from a ledger of what actually happened.**

Everything else in this document is a consequence of that sentence.

---

## Part 1 — What was wrong before

The old model had three things welded together:

```
┌─────────────────────────────────────────────────────────┐
│  OLD: trip.status IS the state machine                  │
│                                                         │
│  created → origin_gate_in → loading → origin_gate_out   │
│          → in_transit → dest_gate_in → unloading        │
│                                                         │
│  advance_h2() asks: "is status exactly 'origin_gate_in'?"│
│                     "then set it to 'loading'."          │
└─────────────────────────────────────────────────────────┘
```

Three failures, all the same root cause:

| # | Problem | Where it bit |
|---|---------|--------------|
| 1 | `trip.status` was both the **description** and the **sequencer** | `advance_h1..h5` branched on it |
| 2 | DB had `UNIQUE(trip_id, handshake_type)` — **one `loading` row per trip** | schema |
| 3 | Frontends counted to five — `Record<1\|2\|3\|4\|5, string[]>`, URL `/trip/handshake/[h]/...` | both apps |

**The wall:** Cape Town → Bloemfontein → Johannesburg, dropping *and* collecting at Bloem, needs **two loadings and two unloadings**. The database couldn't store it. `trip.status` couldn't be `loading` twice. The driver app had no URL for it.

That's a cross-dock — the single most normal thing in South African linehaul. The old model couldn't represent it.

## Part 2 — The new model in three ideas

### Idea 1 — The plan is DATA, written once at trip creation

When a dispatcher creates a trip, the backend immediately writes **every phase row the trip will ever need**, all `pending`.

```
CREATE TRIP ────► generate plan ────► write N rows, all `pending`
                        │
                        └─ N is computed from the stops + consignments.
                           N is NOT a constant. N is NOT 6.
```

### Idea 2 — The ledger is the truth

`phase_events` is an append-and-fill-in ledger. One row per phase per stop.
Completion *fills a row in*. Nothing ever inserts a phase row after creation.

### Idea 3 — Position is DERIVED, never stored

```
current phase  =  the lowest-sequence_number row that is not yet resolved
next phase     =  the same row  ←  one query answers both endpoints
```

`trip.current_phase` / `trip.current_stop` **do exist** as columns — but they are **caches**, rebuilt from the ledger on every completion. No write path is allowed to branch on them.

> **The line to say out loud in the presentation:**
> *"A stored status can drift from what actually happened. A derived one can't. For an evidence system that difference is the entire product."*

## Part 3 — The plan generator (the heart of it)

**File:** `backend/app/orchestration/phase_plan.py` — 96 lines, pure, no database.
It's deliberately DB-free so it's testable and defensible as a function of the route.

### The rule, in English

```
Emit `trip_creation` once, with no stop.

Then FOR EACH STOP in sequence:
    if it's the FIRST stop  →  emit `activation`
    else if anything is dropped here  →  emit `unloading`

    if anything is collected here     →  emit `loading`

    if this is NOT the last stop      →  emit `departure` + `in_transit`
    else                              →  emit `unloading` (if nothing was dropped yet)
                                          emit `confirmation`

sequence_number = the row's index in the emitted list.
```

Two details that matter more than they look:

- **`in_transit` anchors to the stop it DEPARTS FROM**, not the one it arrives at. `in_transit` at stop 1 = "the leg leaving stop 1". This is what makes `trip_creation` the **only** row with a NULL stop — which is what lets one partial unique index prevent duplicate P0 rows (Postgres treats NULLs as distinct, so a plain unique constraint would not).
- **The final stop always closes the chain**, even on an empty repositioning run — otherwise the ledger would end with no unloading and stop being "the complete story".

### Worked examples (these are real — generated by running the actual function)

**Single-leg, loaded — 7 rows.** This is what your dispatcher UI creates today.

```
seq  phase           stop
────────────────────────────
 0   trip_creation    —
 1   activation       0
 2   loading          0
 3   departure        0
 4   in_transit       0     ← the leg leaving stop 0
 5   unloading        1
 6   confirmation     1
```

**Three-stop cross-dock — 11 rows.** A: 0→2 straight through · B: 0→1 dropped at the hub · C: 1→2 collected at the hub.

```
seq  phase           stop
────────────────────────────
 0   trip_creation    —
 1   activation       0
 2   loading          0      ← A and B load here
 3   departure        0
 4   in_transit       0
 5   unloading        1      ← B delivers at the hub
 6   loading          1      ← C collects at the hub      ⭐ SECOND loading
 7   departure        1
 8   in_transit       1
 9   unloading        2      ← A and C deliver            ⭐ SECOND unloading
10   confirmation     2
```

**⭐ That is the whole thesis on one screen.** `loading` twice, `unloading` twice, in one trip, in one table, with no schema change and no new code path.

**Empty leg (repositioning, no cargo) — 6 rows.**

```
seq  phase           stop
────────────────────────────
 0   trip_creation    —
 1   activation       0
 2   departure        0      ← no `loading` row: nothing is collected
 3   in_transit       0
 4   unloading        1      ← emitted anyway, to close the chain
 5   confirmation     1
```

> ⚠️ **This shape currently cannot be completed.** See Finding **F1** in Part 9.

> ⚠️ **Stop numbers differ depending on how the trip was made.** `create_trip` (the HTTP path) numbers stops **from 0** (`trip_service.py:235-236`); `scripts/seed_trips.py:92` numbers them **from 1**. Each path is internally consistent, so nothing is broken — but the demo trips on screen say "Stop 1, Stop 2, Stop 3" while a trip you create live in the same session says "Stop 0, Stop 1". Logged as **NEW-18** in the Stage 4 ledger, deliberately not fixed there (it's a write-path change). The nasty corollary is also recorded: **`current_stop === 0` is falsy in JavaScript**, so any "tidy-up" of the `=== null` checks in `page.tsx` to a truthiness test would silently drop the origin stop on every HTTP-created trip.

### The sentence that proves it's one code path

> **"The single-leg trip is the degenerate case of the multi-stop plan."**

The 7-row plan isn't a special case with a fallback — it's what the multi-stop generator emits when you give it two stops. One rule, forever.

### ⚠️ When is a cross-dock ONE trip, and when is it two? — expect this question

This is the sharpest challenge you can be given, so have the answer ready.

**The challenge:** *"Loaded in Joburg, unloaded in Bloem, reloaded in Bloem, unloaded in Durban — that's two trips. You've merged two trips into one record."*

**The answer: for that description, the challenger is right — and it isn't the shape this model was built for.** The distinction is one question:

> **Does any consignment satisfy `pickup_stop < hub < delivery_stop`?**
>
> **No** → nothing rides through. It's a pure relay. **That is two trips**, and merging them is wrong.
> **Yes** → something never leaves the truck. **It must be one trip.** There is no honest alternative.

Look at what the seeder actually encodes (`scripts/seed_trips.py:216`) — this is the case the refactor exists for:

```
("MOCKWB0005", 1, 3),   # A: straight through   ← NEVER LEAVES THE TRUCK
("MOCKWB0006", 1, 2),   # B: dropped at the hub
("MOCKWB0007", 2, 3),   # C: collected at the hub
```

**Consignment A is the entire justification.** Split that route into two trips and you must either:

1. **fabricate a delivery and a re-collection for A at Bloemfontein** — inventing custody events that never physically happened, which for an evidence product is disqualifying; or
2. leave A's custody chain **dangling across two unlinked records**, so the system can no longer answer *"was this box on the truck the whole time?"* — which is the only question the product exists to answer.

Both are worse than an 11-row plan.

**The deeper reason — the seal chain.** Per `docs/design-notes/2026-06-24-multi-stop-handshakes.md` §3.3, what binds a multi-stop route into one record is that the seal is a *chain*: applied at JHB, broken at BFN, **resealed** at BFN, verified at DBN. Every segment becomes independently provable, *and the chain links them*. Two separate trip records have nothing proving the Bloemfontein handover was continuous — you'd have one trip closing and another opening, with an evidentiary gap in between.

> **The line to say:** *"Splitting is right when nothing rides through. The moment one consignment rides through the hub, splitting requires you to fabricate a delivery that never happened — and an evidence system that fabricates events isn't one."*

**Where the criticism genuinely lands — concede this, don't defend it.** Nothing in the system *enforces* any of the above. There is no validation that a multi-stop trip contains through-freight justifying it, so a dispatcher could merge two commercially separate jobs into one record. Consequences: one journey lock hash binding unrelated commercial jobs, and client A's evidence bundle containing client B's stops. Logged as **F9** in Part 9.

Note also what is *not* wrong: `build_phase_plan` handles the pure-relay case correctly — it emits `unloading(1)` then `loading(1)`, which is physically exactly what happens. **The generator isn't wrong; the trip boundary is a business decision the model doesn't police.** That's the precise scope of the gap.

*Honest counter-argument, in case it's raised:* the vehicle, driver and GPS trace are continuous across a pure relay, so splitting loses the Bloemfontein turnaround. It's not persuasive — the product is cargo custody, not vehicle utilisation — but it isn't a clean 100–0 and you shouldn't pretend it is.

*(Currently theoretical: per **F2**, the dispatcher wizard can't create either shape yet.)*

## Part 4 — Trip creation, step by step

**File:** `backend/app/orchestration/trip_service.py:153` — `create_trip()`

```
 1.  Validate driver, horse, trailers exist and belong to this org
 2.  Reject a duplicate active order_number (coarse statuses: created/active/exception_hold)
 3.  INSERT Trip  (status = 'created')
 4.  INSERT TripTrailer rows  — snapshots the Pulsit device id so a later
                                vehicle swap can't rewrite the evidence chain
 5.  INSERT TripStop rows     — payload.stops if given,
                                else synthesise [origin, destination]
     ── flush ──               (needed: evidence_artifacts has a circular FK back to trips)

 6.  Sync every consignment from Parcel Perfect
     ⚠ FAIL-CLOSED and ATOMIC — any PP error rolls the WHOLE trip back.
       A trip whose cargo plan couldn't be pulled has no manifest and no evidence value.

 7.  Stamp each consignment: pickup_stop_id = first stop, delivery_stop_id = last stop
     ⚠ hardcoded — see Finding F2

 8.  BUILD THE PHASE PLAN  ← _build_phase_events() → build_phase_plan()
     INSERT every row, all `pending`
     anchor_status = 'pending' for the 3 anchored types, 'not_required' for the rest

 9.  Compute the journey lock hash over the immutable trip params
10.  Anchor it to Hedera HCS  ⚠ FAIL-CLOSED — a Hedera failure rolls the trip back
11.  Reaching this line means the anchor succeeded, so trip creation IS P0's completion:
        phase_events[0].status        = completed
        phase_events[0].completed_at  = now
        phase_events[0].anchor_status = anchored
        phase_events[0].blockchain_receipt_id = receipt.id

12.  recompute_position(trip)  ← seed the cache from the ledger
        → current_phase = 'activation', current_stop = 0

13.  Return TripDetailResponse with the FULL plan in `.phases`
```

**Step 11 is the bit worth understanding.** P0 is not something a driver does. Creating the trip *is* the P0 event. If P0 stayed `pending`, the gate ("every lower sequence must be resolved") would block every later phase forever — because P0 is sequence 0, the lowest possible.

## Part 5 — Completing a phase

**File:** `backend/app/orchestration/phase_service.py`

### The API surface (only three routes now)

```
GET  /api/v1/trips/{id}/phases                          → PhaseDescriptor[]   (the plan + state)
GET  /api/v1/trips/{id}/phases/next                     → PhaseDescriptor | null
POST /api/v1/trips/{id}/phases/{phase_event_id}/complete → TripDetailResponse
```

The five `/handshakes/h{n}/complete` routes are **gone**. The dispatcher never calls these — it reads the same plan off `TripDetailResponse.phases` on `GET /trips/{id}`, which it already fetches.

### What `complete_phase()` does

```
complete_phase(trip_id, phase_event_id, payload)
   │
   ├─ 0. Verify the trip belongs to this driver         (404 if not — before anything else,
   │                                                     so a wrong phase_type can't be used
   │                                                     to probe a foreign trip's plan)
   ├─ 0b. body.phase_type must match the ROW's type     (409 otherwise)
   │      trip_creation / in_transit have no wrapper → always 409
   │
   └─ dispatch to one of five wrappers ───────────────┐
                                                      │
   ┌──────────────────────────────────────────────────┘
   │  _gate_and_load()   ← shared, identical for all five
   │     1. load trip + phase event
   │     2. IDEMPOTENCY: already completed/exception/overridden?
   │        → return current state, 200, stop here.        (checked FIRST, on purpose)
   │     3. reject a closed / cancelled / exception_hold trip → 409
   │     4. THE GATE: every row with a lower sequence_number
   │        must be resolved → else 409
   │        ⭐ this reads the PLAN. It never reads trip.status.
   │           That one line IS the refactor.
   │
   │  wrapper body        ← the ONLY per-phase part: writes its own evidence,
   │                        sets its own status (COMPLETED or EXCEPTION)
   │
   │  _finish_phase()     ← shared again
   │     stamp idempotency_key + completed_at
   │     recompute_position(trip)   ← rebuild the cache from the ledger
   │     if nothing unresolved remains → trip.status = closed, closed_at = now
   │     return the fresh TripDetailResponse
   └───────────────────────────────────────────────────
```

**Why idempotency is checked before the trip-status check:** a phase whose own completion *closed* the trip (confirmation) must still replay as a 200, not a 409 — even though `trip.status` now reads `closed` *because of that very completion*. Drivers lose signal; a resent offline-queue entry is normal, not exceptional.

**Why `confirmation` no longer says "I close the trip":** it doesn't. `recompute_position` finds no unresolved rows and closes the trip generically. Confirmation stopped hardcoding "I am always last" — which is exactly what a plan-driven model requires.

## Part 6 — What each phase captures

| # | Phase | Who acts | Evidence written | Hedera |
|---|-------|----------|------------------|--------|
| P0 | `trip_creation` | dispatcher | journey lock hash over committed trip params | ✅ `JOURNEY_LOCK` — **fail-closed** |
| P1 | `activation` | driver | phone GPS lat/lng | — |
| P2 | `loading` | *(system, intended)* | `driver_visual_count` **only** — see F3 | — |
| P3 | `departure` | driver | **`seal_number`**, seal photo, waybill photo, guard seal re-entry | ✅ `PICKUP` — fail-open |
| P4 | `in_transit` | system | auto-completed on departure — see F4 | — |
| P5 | `unloading` | driver | `seal_number_at_destination`, compared to this leg's departure seal | — |
| P6 | `confirmation` | driver | POD photo **and** POD signature, counts, reconciliation | ✅ `DELIVERY` — fail-open |

### The seal moved from loading to departure — say this deliberately

The old H2 anchored `{seal_number, driver_visual_count}` at loading. After the refactor, loading is meant to be system-observed (no driver input at all), so a P2 payload would have had nothing driver-attested left in it. **The seal is physically applied when the driver closes the trailer at the exit gate — which is departure.** So the anchor moved with the evidence.

Net anchors per trip: still two (plus P0). Unchanged. But now they sit where the evidence actually is.

### Seal continuity — two different rules

| Where | Rule | Consequence |
|-------|------|-------------|
| **Departure** (`phase_service.py:425`) | guard's re-entered seal vs. the seal in the *same request* | mismatch → `EXCEPTION` row + `TripException`, but **trip still departs** and **still anchors** |
| **Unloading** (`phase_service.py:493`) | seal at destination vs. **this leg's** departure seal | mismatch → `EXCEPTION` + `trip.status = exception_hold` — **trip is held** |

A departure mismatch is a paperwork anomaly. A destination mismatch means the trailer was opened in transit. Different severity, different handling. Good design — make this point.

### "This leg's", not "the trip's"

`_find_departure_for_leg()` and `_find_loading_for_leg()` both search **backwards from the row being completed** for the nearest matching row:

```python
.where(phase_type == DEPARTURE, sequence_number < before_sequence)
.order_by(sequence_number.desc()).limit(1)
```

On a cross-dock there are two departures and two loadings. A naive trip-wide `phase_type == 'loading'` lookup raises `MultipleResultsFound` on every real multi-stop trip. This is the kind of thing that only shows up once the plan actually varies in length — a good example of "the refactor forced us to get this right".

### Fail-open vs fail-closed (`_anchor_or_fail_open`, `phase_service.py:184`)

```
P0  fail-CLOSED  →  Hedera down = no trip. Nothing committed yet, nothing to salvage.
P3  fail-OPEN    →  Hedera down = the phase STILL COMPLETES.
P6  fail-OPEN       anchor_status = 'failed'; a receipt is owed and the system knows it.
```

Driver custody doesn't pause because Hedera is slow. A seal event is evidence that *already happened*. But a completed phase with a failed anchor must **never render as an unqualified success** — the dispatcher UI prints `⚠ Anchor failed — receipt owed` (`page.tsx:416`) and the sidebar tally counts it (`derive.ts:96`).

## Part 7 — How the dispatcher UI reads it

**Files:** `frontend/dispatcher/lib/phase/derive.ts` (pure, unit-tested) and `app/(app)/trips/[id]/page.tsx`

```
GET /trips/{id}
   └─ .phases: PhaseDescriptor[]
        │
        ├─ sortedPlan()        never trust wire order — sort by sequence_number
        ├─ activePhase()       lowest-sequence unresolved row
        ├─ nodeTypeFor()       done / active / warn / pending per row
        ├─ currentSealNumber() the HIGHEST-sequence completed departure's seal
        │                      (a cross-dock carries a different seal per leg)
        ├─ originParcelCount() the LOWEST-sequence loading's count
        │                      (the hub pickup is a different, later row)
        └─ anchorTally()       owed / anchored / failed, from anchor_status —
                               never from plan length
```

Timeline rendering, `page.tsx:393`:

- Cards are keyed on **`phase_event_id`**, never on index or `phase_type`. That's what lets two `loading` rows on a cross-dock each open **their own** manifest slice.
- The node's number is `phase.sequence_number` — read straight off the plan.
- Each row's label is `PHASE_NAMES[phase.phase_type]`; its subtitle is `Stop N · <precinct>` — the stop is what disambiguates two identically-named rows.
- Each departure card shows **its own** seal, so a cross-dock visibly carries a different seal per leg. *That is the multi-stop proof on screen.*
- Trip-detail derives the active phase from the plan and **must not** use `trip.current_phase` (the U3 fence). The trip **list** is allowed the cache — it has no plan.

**Nothing on this page may assume six phases.** The rail length is `plan.length`; the progress denominator is the plan's own length.

## Part 8 — Manifests and waybills: the honest answer

You asked specifically about this. Here is exactly what the system does — and does not — do.

### The data model

```
Trip
 └── Consignment          ← one per PP waybill  (parcel_perfect_reference)
      │    pickup_stop_id  ──┐  the two FKs that make a stop an "origin" or
      │    delivery_stop_id ─┘  a "destination". A TripStop has no inherent role.
      │    unit_count_expected  ← dispatcher-entered PALLET count; PP has no pallet grain
      └── Parcel           ← one per PP barcode
            barcode
            delivery_stop  ← ⚠ a plain STRING from PP (a town name), NOT a TripStop FK
            pp_scan_out_at ← proves it left the origin
            pp_scan_in_at  ← proves it arrived
```

### The endpoint is role-split, and that's deliberate

`GET /api/v1/trips/{id}/manifest` returns **two different shapes depending on who asks**:

| Caller | Returns | Contains |
|--------|---------|----------|
| **Dispatcher** | `ManifestResponse` | every consignment, every parcel, every barcode, per-stop grouping, scan timestamps |
| **Driver** | `LinehaulResponse` | **one consolidated pallet number.** No barcodes. No parcel list. No per-parcel data at all. |

> **This is a theft-risk control, not a UI convenience.** (Bruce, 24 Jun; `manifest_service.py:1`.) A driver who can see per-parcel detail knows exactly which pallet is worth stealing. The driver counts **pallets**, never parcels. And the driver never sees the expected count either — if the expected number is visible, a "match" proves nothing. The server reconciles privately at confirmation and returns only a verdict.

Empty legs return a **defined zero**, not a 404 — "no cargo by definition" is an answer, not a failure.

### How it surfaces at loading / unloading in the trip detail page

Clicking a `loading` or `unloading` card opens `ManifestPanel` (`page.tsx:486` → `ManifestPanel.tsx`):

```
┌─ Manifest · Loading · Stop 0 · Cape Town ────────────┐
│                                                      │
│  "This is the full trip manifest. Parcel Perfect     │  ← stated in the UI,
│   does not break parcels down per stop."             │    ManifestPanel.tsx:62
│                                                      │
│  [unloading only] Reconciliation                     │
│     Counted at destination   —                       │  ← see F5
│     Driver visual count      —                       │
│                                                      │
│  ▸ MOCKWB0001    3 units · 12 parcels                │
│     └ Johannesburg · 12                              │
│         ● FP00000001   06:12   ← scan-out at loading │
│         ○ FP00000002   pending                       │
│                                                      │
│  Total                              12 parcels       │
│  Origin scan complete ✓                              │
└──────────────────────────────────────────────────────┘
```

The one genuinely clever bit: `ParcelRow` switches which timestamp it reads based on the mode —

```ts
const scanAt = mode === 'loading' ? parcel.pp_scan_out_at : parcel.pp_scan_in_at
```

Loading is proven by scan-**out**; unloading by scan-**in**. Showing the wrong column would make an unscanned parcel look accounted for.

### ⚠️ Expected vs. actual — do NOT claim this shows what was scanned

The natural assumption is: *expected consignments are attached at trip creation, and then at loading/unloading the panel shows the waybills **actually** scanned on and off the truck.*

**That is the design. It is not the behaviour.** The panel shows the **expected** set at loading and at unloading alike.

| | Reality |
|---|---|
| `pp_scan_out_at` / `pp_scan_in_at` | **read in 3 places, written in 0** — no code path in `backend/app/` ever sets them |
| `Parcel` creation (`consignment_service.py:214`) | every row created `status=PENDING`, both scan timestamps null |
| The Celery re-poll (`tasks/parcel_perfect.py`) | refreshes active trips and adds newly-appeared barcodes; **never sets scan times** |
| `PPTrack` (`integrations/parcel_perfect.py:75`) | carries `trackno`, `parcelno`, `item` — **no status, no timestamp**. PP doesn't supply the data. |

So on any real trip every parcel dot is grey and `origin_scan_complete` is always `false`. The green "scanned" dots you have seen on screen exist **only because `seed_trips.py` fakes them**.

The root cause is upstream and the parent plan states it plainly: *"No live PP load/unload status — it does not exist (spec §6)."* The reconciliation columns are wired and waiting on a capability that isn't there.

> **What to say in the demo:** *"This is the committed manifest from Parcel Perfect. The scan-reconciliation columns are wired; they're waiting on a PP scan-event feed that doesn't exist yet."*
>
> **What not to say:** *"This shows what was actually scanned onto the truck."*

This is the same hole as **F3** surfacing in a second place — `parcel_count_origin`, the field that would carry "how many actually loaded", is likewise written only by the seeder. Closing it properly needs either a PP scan-event feed or capturing the warehouse scan directly. That's a scope decision, not a bug fix.

### ⚠️ The other honest limitation — say this before someone asks

**The manifest is trip-scoped, not phase-scoped or stop-scoped.**

Both `loading` cards on a cross-dock open **the same full trip manifest**. Parcel Perfect gives no per-stop split, so the system doesn't invent one. The panel says so in plain text rather than letting a dispatcher infer a per-stop breakdown that doesn't exist.

The data to do better *nearly* exists — `Consignment.pickup_stop_id` / `delivery_stop_id` are already populated, so you could filter consignments per stop. What's missing is at the parcel grain: `Parcel.delivery_stop` is a free-text town name from PP, not a `TripStop` FK.

**Waybill *photos* are separate from waybill *data*.** The photo is `waybill_photo_artifact_id`, captured at **departure** (P3), stored in Supabase Storage and rendered via short-lived signed URLs (`useTripArtifacts`). The waybill *data* is the PP consignment pulled at creation. Two different things with the same name — worth being precise about if you're asked.

### 🔴 F1 — An empty-leg trip can never be closed — **not in any ledger; this one is new**

An empty leg generates no `loading` row (verified in Part 3). `advance_confirmation` unconditionally calls `_find_loading_for_leg()` (`phase_service.py:552`), which raises `ResourceNotFoundError` when no loading row exists → **404**. Create an empty leg, walk it to confirmation, and it 404s forever. The trip can never reach `closed`.

**Why it slipped through, and why that's instructive.** Stage 2's plan (`…stage-2-phase-engine.md:421`) *does* consider empty legs — and concludes: *"Already handled and unit-tested by `build_phase_plan` … No new code needed for this case — it falls out of the existing generator."* That is **true for plan generation** and `test_empty_leg_plan_still_closes_custody` proves it. But the check stopped at generation and never asked whether the resulting plan could be **completed**. `_find_loading_for_leg` was written later, in Stage 3, to fix a *different* problem (NEW-9's `MultipleResultsFound` on cross-dock trips) — and its `Optional`-less contract quietly broke the shape Stage 2 had already signed off.

That's a good story to be able to tell: the gap wasn't carelessness, it was a correct verification aimed one layer too early.

*Fix shape:* make `_find_loading_for_leg` return `Optional[PhaseEvent]`, and skip count reconciliation when there is nothing to reconcile. An empty leg has no counts by definition. Add an integration test that walks an empty leg to `closed`.

### 🟠 F2 — The dispatcher UI cannot create a multi-stop trip

The cross-dock capability — the entire thesis of the refactor — is **only reachable from the seed script**.

- `frontend/dispatcher/app/(app)/trips/new/page.tsx:390` sends `origin_precinct_id` + `destination_precinct_id`. It never sends `stops[]`.
- `TripCreateRequest.stops` exists and works (`schemas/trips.py:294`) — the wizard just has no UI for it.
- Worse, even if it did: `TripConsignmentInput` (`schemas/trips.py:273`) carries **only** `pp_reference` + `unit_count_expected`. There is no per-consignment stop reference. So `create_trip` hardcodes every consignment as first-stop → last-stop (`trip_service.py:305`).

**Consequence:** a 3-stop trip created through the API today produces this plan —

```
0 trip_creation · 1 activation(0) · 2 loading(0) · 3 departure(0) · 4 in_transit(0)
· 5 departure(1) · 6 in_transit(1) · 7 unloading(2) · 8 confirmation(2)
```

— stop 1 is a **pass-through with no loading and no unloading**, because every consignment was stamped 0→2. Not a cross-dock. Two consecutive transit legs.

**To make the demo's headline claim reachable from the UI, three things must change together:**

1. `TripConsignmentInput` gains `pickup_stop_sequence` / `delivery_stop_sequence` (with the current first→last as the default).
2. `create_trip` stamps from those fields instead of `trip_stops[0]` / `trip_stops[-1]`.
3. The wizard's Step 3 becomes an ordered stop list, and Step 1 gains a per-waybill "picks up at / drops at" selector.

Also worth flagging: the journey lock hash (`trip_service.py:327`) covers only `origin_precinct_id` and `destination_precinct_id` — **the intermediate stops and the phase plan are not in the hash.** The code says so honestly ("FP-113 extends it to cover the full route; no real multi-stop trip should be anchored before that lands"). For an evidence system whose central claim is a tamper-evident committed route, that's a real gap. Expect a question on it.

### 🔴 F2b — `NEW-17`: reconciliation gives a **false mismatch** on a multi-pickup → multi-drop trip

Already logged (Stage 3 ledger, raised by you 2026-07-29, deliberately not fixed — recorded as a product decision). I'm restating it because it is arguably the most serious open item in the backend and it belongs next to F2.

`_find_loading_for_leg` resolves the **nearest preceding** loading. That's right for the hub shape it was reasoned against. It is **wrong** for collect-at-several-stops-then-deliver-at-several — e.g. collect at Fedex JHB (0) and RTT JHB (1), deliver at RTT DBN (2) and Fedex DBN (3):

```
0 trip_creation  1 activation(0)  2 loading(0)  3 departure(0)  4 in_transit(0)
5 loading(1)     6 departure(1)   7 in_transit(1)
8 unloading(2)   9 departure(2)  10 in_transit(2)
11 unloading(3) 12 confirmation(3)
→ confirmation at seq 12 resolves LOADING seq 5 (RTT JHB). WRONG CONSIGNMENT.
```

The final leg has no loading of its own, so "nearest preceding" reaches back to an unrelated pickup. **It doesn't skip a check — it raises a false `WAYBILL_COUNT_MISMATCH` on a correct delivery.** The ledger would record an anomaly that didn't happen, which for an evidence system is worse than no check at all.

The ledger's own conclusion is the right one and worth quoting if asked: *"The fix is not a better sequence heuristic. Reconciliation must be per consignment, not per leg."* The data is already there — `Consignment.pickup_stop_id` / `delivery_stop_id` answer it directly with no inference from `sequence_number`.

Note this is **not** a Stage 3 regression: the old trip-wide `.scalar_one()` would have crashed on this shape. Stage 3 turned a crash into a plausible-but-wrong number — harder to notice, which is exactly why it was written down.

### 🟡 F9 — Nothing enforces that a multi-stop trip *should* be one trip

Raised as a challenge to the model (see Part 3, "When is a cross-dock one trip and when is it two?"). The model's answer is correct — through-freight makes one trip mandatory, because splitting would require fabricating a delivery that never happened — but **the system never checks that through-freight exists.**

A dispatcher can put three stops on a trip where every consignment is `stop 0 → stop 1` or `stop 1 → stop 2` and nothing rides through. That's a pure relay: commercially two jobs, recorded as one. Consequences:

- one journey lock hash binds two unrelated commercial jobs;
- client A's evidence bundle contains client B's stops (awkward commercially, and adjacent to the POPIA minimisation posture);
- trip counts, billing granularity and driver-hours reporting are all wrong by one.

**The check is trivial and the data already exists.** At creation, after consignments are stamped:

```
if any intermediate stop has no consignment spanning it
   (i.e. no consignment with pickup_stop < stop < delivery_stop):
       warn — "no cargo rides through stop N; this may be two trips"
```

`Consignment.pickup_stop_id` / `delivery_stop_id` answer it directly with no inference from `sequence_number` — the same fields **NEW-17** says reconciliation should have been using all along.

**Not a defect in `build_phase_plan`.** The generator handles the relay shape correctly (it emits `unloading` then `loading` at the hub, which is physically what happens). The gap is that the *trip boundary* is a business decision the model doesn't police. Currently theoretical — per **F2** the wizard can't create either shape yet — but it should land alongside F2, because F2 is what makes it reachable.

### 🔴 F10 — `EXCEPTION_HOLD` is a permanent dead-end

**The most serious finding in this document, and the one an examiner is most likely to walk into.**

`advance_unloading` sets `trip.status = EXCEPTION_HOLD` on a destination seal mismatch (`phase_service.py:495`). `_gate_and_load` then rejects every subsequent completion (`:136`). And there is no way back out:

| | |
|---|---|
| `PhaseStatus.OVERRIDDEN` | modelled, **read by the gating logic** (`:105`, `:118`, `resource_service.py:114`), **written by nothing** |
| `dispatcher_override_user_id` / `_note` | columns exist, zero write sites |
| `TripStatus.CANCELLED` | read in two places, **never written** |
| `trips.py` routes | 1 POST (create) + 3 GET. No PATCH, no cancel, no override |
| `exceptions.py` | driver-raise only. Its docstring: *"Dispatcher list/resolve/override are out of scope for this plan — flagged, not silently dropped."* |
| every write to `trip.status` in `app/` | `CLOSED` · `ACTIVE` · `EXCEPTION_HOLD`. That's all three. |

**So a trip that detects seal tampering can never be completed, closed, cancelled, or released. It is stuck forever.** That is precisely the scenario FreightProof exists to detect. "What happens when the seal doesn't match?" gets one good sentence and then a dead end.

**Reproduce:** walk any trip to unloading, submit a destination seal that differs from the departure seal, then attempt confirmation → 409, permanently.

There are actually **two** dead-ends with different causes, which is why the fix is two actions rather than one — see Stage 6 **D1**. On the seal path the *phase* row is `EXCEPTION`, which `_is_resolved` already treats as resolved, so the phase isn't what blocks; `trip.status` is. A phase-level override wouldn't fix it. You need a trip-level **release** for that, and a phase-level **override** for the separate case of a phase no driver can complete.

Fixed by Stage 6 task 6.0 — three endpoints, roughly half a day. The cheapest high-value fix on the board.

### 🟠 F11 — No concurrency control anywhere

`grep -rn "with_for_update\|FOR UPDATE" backend/app/` returns **nothing**. Two simultaneous completions of the same pending phase both read it as `PENDING`, both pass the gate, both write evidence, and — the part that matters — **both submit to Hedera**, because `_anchor_or_fail_open` runs before `_finish_phase` flushes the idempotency key. The partial unique index then fires on the second commit and the request 500s, but **a database rollback cannot un-submit an on-chain message**. The orphan receipt is permanent.

Low likelihood in a demo; the fix is one `.with_for_update()` on `_load_phase_event`, after which the second request simply blocks, re-reads the resolved row, and returns the idempotent 200 that already exists. Stage 6 task 6.2.

## Part 13 — The 90-second version for the presentation

> **Slide 1 — the problem.**
> "Our old model hard-coded five handshakes. `trip.status` was both the description of the trip and the state machine that sequenced it, and the database allowed exactly one loading event per trip. That works for a truck going A to B. It cannot represent a truck that drops half its load in Bloemfontein and picks up a new load there — which is the most normal thing in South African linehaul."

> **Slide 2 — what we changed.**
> "We stopped storing where a trip is, and started deriving it. At creation we generate the trip's full phase plan from its stops and its cargo, and write every row up front, all pending. The trip's position is simply the lowest-sequence row that isn't resolved yet."

> **Slide 3 — the plan.** *(show the 7-row and 11-row plans side by side)*
> "Two stops gives seven rows. A three-stop cross-dock gives eleven, and contains loading twice and unloading twice. Same generator, same table, same code path. The single-leg trip is just the degenerate case of the multi-stop plan."
